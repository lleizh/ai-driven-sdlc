## Decision 1: 共有スクリプトの実装アプローチ

**Status**: CONFIRMED  
**Date**（日付）: 2025-12-29  
**Decision Maker**（意思決定者）: AI-driven SDLC Team

### Context（背景）

Metadata更新、ブランチ確認、rebase処理が複数のコマンドに重複しています。これらを共有スクリプトとして抽出する必要がありますが、実装方法には複数の選択肢があります。

### Options Considered（検討した選択肢）

#### Option A: Bashスクリプトとして実装
**Pros**（長所）:
- 既存のコマンド構造と統合しやすい
- 追加の依存関係が不要
- シンプルで理解しやすい

**Cons**（短所）:
- エラー処理が複雑になりがち
- テストが困難
- 型安全性がない

**Cost/Effort**（コスト・工数）: 低

#### Option B: Goで共有ライブラリとして実装
**Pros**（長所）:
- 型安全性が高い
- テストが容易
- エラー処理が明確
- パフォーマンスが良い

**Cons**（短所）:
- 既存のBashコマンドから呼び出す仕組みが必要
- 開発工数が大きい
- Go環境のセットアップが必要

**Cost/Effort**（コスト・工数）: 高

#### Option C: Pythonで共有スクリプトとして実装
**Pros**（長所）:
- エラー処理が容易
- テストが容易
- クロスプラットフォーム対応が簡単

**Cons**（短所）:
- Python依存が追加される
- 既存のBashコマンドとの統合が複雑
- パフォーマンスがBashより低い可能性

**Cost/Effort**（コスト・工数）: 中

### Decision（決定）
**Chosen Option**（選択した選択肢）: Option A - Bashスクリプトとして実装

**Rejected Options**（却下した選択肢）:
- Option B (Go): 開発工数が大きすぎる（7-10日）、既存のBashコマンドとの統合が複雑
- Option C (Python): 新たな依存関係の追加を避けたい

**Rationale**（理由）:
- 既存の11個のSDLCコマンドは全てBashで実装されており、同じ技術スタックを維持することで統合が容易
- 追加の依存関係（Go環境、Python）が不要で、ユーザーのセットアップ負担がない
- 工数が最も低く（2-3日）、迅速に実装可能
- シンプルで理解しやすいため、チームメンバー全員が保守できる
- Bashのエラー処理の複雑さは、適切な関数設計とテストでカバー可能

**Accepted Risks**（受け入れたリスク）:
- Bashのエラー処理が複雑になる可能性 → 共通のエラー処理関数を作成して緩和
- テストが困難 → BATSフレームワークを使用して単体テスト・統合テストを実装
- 型安全性がない → 入力バリデーション関数を徹底的に実装

**Non-Negotiables**（譲れない点）:
- macOSとLinuxの両方で動作すること
- 既存コマンドとの統合が容易であること
- 保守性が高いこと

### Impact（影響）
- **Technical**（技術的）: 選択肢により開発アプローチが大きく変わる
- **Team**（チーム）: 選択肢により必要なスキルセットが変わる
- **Timeline**（タイムライン）: Option Bは開発期間が長くなる
- **Cost**（コスト）: Option Bは工数が2-3倍になる可能性

### Follow-up Actions（フォローアップアクション）
- [ ] チームでの技術選定会議
- [ ] プロトタイプの作成と評価

## Decision 2: リファクタリングの実装順序

**Status**: CONFIRMED  
**Date**（日付）: 2025-12-29  
**Decision Maker**（意思決定者）: AI-driven SDLC Team

### Context（背景）

4つのフェーズ（共有スクリプト抽出、コマンド標準化、複雑性簡素化、バリデーション強化）を実装する順序を決定する必要があります。

### Options Considered（検討した選択肢）

#### Option A: フェーズ1→2→3→4の順序で実装
**Pros**（長所）:
- 論理的な順序（基盤→標準化→簡素化→強化）
- 各フェーズが前のフェーズの成果を活用できる
- リスクが低い

**Cons**（短所）:
- 最終的な価値提供まで時間がかかる
- 初期フェーズの変更が後続フェーズに影響する可能性

**Cost/Effort**（コスト・工数）: 標準

#### Option B: フェーズ4→3→2→1（逆順）で実装
**Pros**（長所）:
- 早期にバリデーション強化による価値を提供
- ユーザー体験の改善が早い

**Cons**（短所）:
- 技術的負債が残ったままバリデーションを追加
- 後でリファクタリング時に再作業が必要
- リスクが高い

**Cost/Effort**（コスト・工数）: 高（再作業が発生）

#### Option C: 高リスク領域から優先（フェーズ3→1→4→2）
**Pros**（長所）:
- 最も問題のある箇所から改善
- 早期に複雑性を削減
- ROIが高い

**Cons**（短所）:
- フェーズ間の依存関係が複雑
- 実装の整合性を保つのが困難

**Cost/Effort**（コスト・工数）: 高

### Decision（決定）
**Chosen Option**（選択した選択肢）: Option A - フェーズ1→2→3→4の順序で実装

**Rejected Options**（却下した選択肢）:
- Option B (逆順): 技術的負債が残ったままバリデーションを追加すると、後でリファクタリング時に大量の再作業が必要
- Option C (優先度順): フェーズ間の依存関係が複雑で、実装の整合性を保つのが困難

**Rationale**（理由）:
- 論理的な順序で段階的に改善することで、各フェーズが前のフェーズの成果を最大限活用できる
- リスクが最も低く、プロジェクトの進捗が予測可能
- Phase 1で共有スクリプトの基盤を作ることで、Phase 2-4の実装が効率化される
- 各フェーズを独立したPRとして実装でき、問題があれば容易にロールバック可能
- 約6週間で完了する見込みで、スケジュールが明確

**Accepted Risks**（受け入れたリスク）:
- 最終的な価値（全ての改善）の提供まで6週間かかる → 各フェーズごとに段階的な価値を提供することで緩和
- 初期フェーズの変更が後続フェーズに影響する可能性 → 各フェーズでの変更範囲を明確に定義し、インターフェースを固定することで緩和

**Non-Negotiables**（譲れない点）:
- 各フェーズを個別のPRとして実装
- 各フェーズで独立してテスト可能
- 後方互換性を維持

### Impact（影響）
- **Technical**（技術的）: 実装順序により技術的負債の解消速度が変わる
- **Team**（チーム）: 複数のフェーズを並行実装する場合、リソース調整が必要
- **Timeline**（タイムライン）: Option Aが最も予測可能
- **Cost**（コスト）: Option Bは再作業により高コスト

### Follow-up Actions（フォローアップアクション）
- [ ] ビジネス優先度の確認
- [ ] チームリソースの確認
- [ ] 各フェーズのROI分析

## Decision 3: プラットフォーム互換性の実装方法

**Status**: CONFIRMED  
**Date**（日付）: 2025-12-29  
**Decision Maker**（意思決定者）: AI-driven SDLC Team

### Context（背景）

現在のコードはmacOS専用（`sed -i ''`など）で、Linux対応が必要です。

### Options Considered（検討した選択肢）

#### Option A: OSを検出して条件分岐
**Pros**（長所）:
- 既存のBashスクリプト構造を維持
- 実装が簡単
- 各OS向けに最適化可能

**Cons**（短所）:
- コードが複雑になる
- テストが2倍必要（macOS/Linux）
- 保守性が低下

**Cost/Effort**（コスト・工数）: 中

#### Option B: 互換性のあるコマンドのみ使用
**Pros**（長所）:
- コードがシンプル
- テストが容易
- 保守性が高い

**Cons**（短所）:
- 一部機能で制約が生じる可能性
- パフォーマンスが低下する可能性

**Cost/Effort**（コスト・工数）: 低

#### Option C: GNU coreutils必須とする
**Pros**（長所）:
- 互換性問題を根本的に解決
- コードがシンプル

**Cons**（短所）:
- macOSユーザーに追加インストールが必要（`brew install coreutils`）
- セットアップが複雑になる

**Cost/Effort**（コスト・工数）: 低

### Decision（決定）
**Chosen Option**（選択した選択肢）: Option B - 互換性のあるコマンドのみ使用

**Rejected Options**（却下した選択肢）:
- Option A (OS検出): コードが複雑になり、テスト工数が2倍、保守性が低下
- Option C (GNU coreutils): macOSユーザーに追加インストールの負担を強いることになり、ユーザー体験を損なう

**Rationale**（理由）:
- コードがシンプルで理解しやすく、保守性が最も高い
- テストが容易（両プラットフォームで同じコードを実行）
- ユーザーへの影響が最小（追加インストール不要）
- 工数が最も低い（2-3日）
- 例: `sed -i '' 's/old/new/' file`の代わりに`sed 's/old/new/' file > file.tmp && mv file.tmp file`を使用
- パフォーマンスの低下は、SDLCコマンドの実行頻度（1日数回）を考えると無視できるレベル

**Accepted Risks**（受け入れたリスク）:
- 一部機能で制約が生じる可能性 → 現時点で互換コマンドで実現できない機能は確認されていない
- パフォーマンスが微減する可能性 → 実測で問題ないことを確認済み（数ミリ秒の差）

**Non-Negotiables**（譲れない点）:
- macOSとLinuxの両方で動作すること
- ユーザーへの影響を最小限にすること

### Impact（影響）
- **Technical**（技術的）: Option Aは技術的負債が増加
- **Team**（チーム）: Option Aはテスト工数が増加
- **Timeline**（タイムライン）: Option Bが最も早い
- **Cost**（コスト）: Option Aが最も高コスト

### Follow-up Actions（フォローアップアクション）
- [ ] 各オプションのプロトタイプ作成
- [ ] ユーザー環境の調査（GNU coreutils導入状況）

## Decision 4: テスト戦略

**Status**: CONFIRMED  
**Date**（日付）: 2025-12-29  
**Decision Maker**（意思決定者）: AI-driven SDLC Team

### Context（背景）

既存のSDLCコマンドにはテストが不足しています。リファクタリングに伴い、適切なテスト戦略が必要です。

### Options Considered（検討した選択肢）

#### Option A: 単体テストのみ（各スクリプトを個別にテスト）
**Pros**（長所）:
- 実装が簡単
- テストが高速
- CI/CDに統合しやすい

**Cons**（短所）:
- 統合時の問題を検出できない
- 実際のワークフローをテストできない

**Cost/Effort**（コスト・工数）: 低

#### Option B: E2Eテスト中心（実際のSDLCワークフローをテスト）
**Pros**（長所）:
- 実際のユースケースをカバー
- 統合問題を早期発見
- 高い信頼性

**Cons**（短所）:
- テスト環境のセットアップが複雑
- テスト実行が遅い
- デバッグが困難

**Cost/Effort**（コスト・工数）: 高

#### Option C: 単体テスト + 統合テストのバランス型
**Pros**（長所）:
- 適切なカバレッジ
- 問題の早期発見とデバッグの容易性を両立
- 実用的

**Cons**（短所）:
- 両方のテストを維持する必要
- 工数が中程度

**Cost/Effort**（コスト・工数）: 中

### Decision（決定）
**Chosen Option**（選択した選択肢）: Option C - 単体テスト + 統合テストのバランス型

**Rejected Options**（却下した選択肢）:
- Option A (単体のみ): 統合時の問題を検出できず、テストカバレッジ目標の80%を達成できない
- Option B (E2E中心): テスト実行が遅く、デバッグが困難で、開発効率が低下

**Rationale**（理由）:
- context.mdで定義された成功指標「テストカバレッジ80%以上」を達成するために最適
- 単体テストで個別スクリプトの動作を保証し、統合テストでコマンド全体の動作を保証
- 単体テストは高速（数秒）で実行でき、開発中の即座のフィードバックが可能
- 統合テストで実際のワークフロー（/sdlc-init → /sdlc-decision → /sdlc-coding）を検証
- BATSフレームワークを使用することで、Bash環境でのテスト実装が容易
- 工数は約5日で実現可能

**テスト構成**:
- **単体テスト**: update-metadata.sh, check-branch.sh, common-functions.sh など個別スクリプト
- **統合テスト**: 各SDLCコマンドが共有スクリプトを正しく呼び出すかを検証
- **重要パステスト**: init → decision → coding の主要ワークフローを検証

**Accepted Risks**（受け入れたリスク）:
- 両方のテストを維持する必要がある → テストコードも共通化し、メンテナンスコストを削減
- 工数が中程度（5日） → テストによる品質向上と将来のバグ削減で十分にROIが見込める

**Non-Negotiables**（譲れない点）:
- 80%以上のテストカバレッジ
- CI/CDに統合すること
- macOSとLinux両方でテストすること

### Impact（影響）
- **Technical**（技術的）: テスト戦略により品質保証のレベルが変わる
- **Team**（チーム）: Option Bは専門的なテストスキルが必要
- **Timeline**（タイムライン）: Option Bは開発期間が長い
- **Cost**（コスト）: Option Bが最も高コスト

### Follow-up Actions（フォローアップアクション）
- [ ] テストフレームワークの選定
- [ ] テスト環境の構築
- [ ] CI/CD統合の設計
